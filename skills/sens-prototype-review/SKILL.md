# Sens Prototype Review

检查原型是否忠实覆盖需求并正确消费 Sens，而不是仅判断页面能否构建。

## 输入

读取根目录 `AGENTS.md`、需求 `prototype-spec.json`、输入来源、当前原型、安装的 Sens 版本及已有审核记录。来源无法读取时明确标记缺失证据。

## 四类检查

### 需求

- 页面、流程、限制、文案和状态可追溯到 requirement 或已确认回答。
- 改动区域和保留区域没有相互污染。
- PRD、局部 Figma、截图和 Sens 之间的冲突已记录。

### Sens

- 页面使用固定版本 `@sens/prototype-kit` 的公开组件和 Product Shell。
- 业务代码不直接导入 antd，不复制 Sens 组件，不以自定义 CSS 覆盖基础组件状态。
- 组件映射、缺口和例外与实际代码一致。

### 交互

- 主路径可以实际操作，取消、保存、切换和反馈结果一致。
- 必填、长度、格式等本地校验真实触发；模拟成功和失败可重复并可复位。
- 至少检查目标桌面宽度、浮层、滚动、收起与返回路径；不能操作的静帧不标通过。

### 交付

- 类型检查和生产构建通过。
- 浏览器资源、刷新路由和静态产物经过实际检查。
- 本地预览、静态文件和已发布链接使用准确名称。

## 输出规则

每类给出 `pass`、`fail`、`not_run` 或 `blocked`，并附实际证据。优先报告影响业务理解或设计系统一致性的缺陷。没有设计师明确决定时，`designStatus` 保持 `awaiting_designer`。

发现上游 Sens 缺口时，只记录建议和影响，不直接修改 `sens-preview`。若用户要求修复，只修改当前原型范围；需要上游改动时另行请求授权。
