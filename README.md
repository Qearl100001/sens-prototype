# Sens Prototype

面向 PM 的 Sens 交互原型工作流：提交 PRD、现有页面截图及可选的局部 Figma，生成可评审的交互半成品，由设计师最终审核。

## 当前状态 · P0-5 独立交付已完成

已提供：项目入口、需求规格约定、生成 Skill、检查 Skill、固定版本 Sens 资产包、标准原型工程和特征筛选试点。

特征筛选试点使用项目内固定版本 `@sens/prototype-kit 0.1.0-p0.6`，用于验证 PRD、截图、录屏和局部 Figma 可以形成独立、可交互的 Sens 原型。原型不引用 `sens-preview` 源码。

P0-5A 已通过干净副本验证：不携带当前电脑的 `node_modules` 与 `dist`，在临时目录重新安装、构建并检查静态资源。P0-5B 已通过 GitHub Actions 构建并由 GitHub Pages 发布真实分享链接。

代码仓库：[Qearl100001/sens-prototype](https://github.com/Qearl100001/sens-prototype)

交互原型：[特征值单选与多选试点](https://qearl100001.github.io/sens-prototype/)

当前仍未提供：自动生成 CLI 和任意 PRD 的批量生成能力。P0-5 证明当前仓库及试点可以迁移、构建和公开分享，不代表跨宿主或多需求泛化已经完成。

## 项目关系

| 项目 | 负责内容 |
| --- | --- |
| sens-preview | Token、Foundation、组件、复合模式、布局样板及其正式规则与验收 |
| sens-prototype | PM 输入、页面规格、组件匹配、原型生成、检查与交付 |
| 团队需求项目 | 具体原型源码、模拟数据、版本、设计师反馈及部署产物 |

下游消费固定版本的 Sens 资产，不手工复制维护第二套组件，也不依赖同级文件夹相对源码引用作为正式交付方案。

## PM 如何使用

将项目交给支持本地文件和开发工具的聊天宿主，要求其读取 `AGENTS.md`。宿主能否自动发现 Skill、访问 Figma、执行构建或控制浏览器，需要逐一验证；此处不声明所有宿主已经兼容。

示例输入：

> 按这份 PRD 修改截图中的特征值抽屉，其余区域保留。生成支持切换、取消、保存和应用效果的原型。局部 Figma 是新版设计依据。

助手先解释本次变化和关键歧义，再推进已明确的部分。PM不需要编写JSON或指定组件名称。后续修改沿用同一份需求规格和原型项目。

## 六步工作流

| 步骤 | 产物 | 判定 |
| --- | --- | --- |
| 1. 理解输入 | 来源、业务目标、当前页面 | 不把截图或PRD里的推断当成已确认事实 |
| 2. 确定变化 | 改动区域、保留区域、状态、问题 | 关键业务歧义得到回答，或隔离不确定分支 |
| 3. 匹配Sens | 组件与样板映射、版本、缺口 | 必需能力可用；缺口有明确处置 |
| 4. 生成原型 | 页面、模拟数据、交互 | 关键路径可实际操作 |
| 5. 检查修正 | 四类检查及证据 | 未验和失败如实报告，设计师仍有最终审核权 |
| 6. 交付评审 | 项目文件、静态包、预览链接及记录 | 区分本地预览、构建产物和真实已发布链接 |

## 来源如何裁决

- PRD：业务目标、限制、流程与结果。
- 明确的局部 Figma：该区域的新视觉与交互设计。
- 现有页面截图：位置、上下文、保留区域；不用于推断隐藏状态或精确Token。
- Sens：未被明确覆盖的标准布局、基础样式与组件行为。
- 如果局部Figma超出Sens能力，记录例外并交设计师裁决，不静默修改全局规则。
- 同类来源内部矛盾时记录冲突；“已定稿”标签不能消除正文矛盾。

## 规格与需求产物

`contracts/prototype-spec.schema.json` 使用 JSON Schema 2020-12。版本为 `0.1.0`，范围包含需求、来源、页面状态、交互、校验、Sens匹配、问题和审核。

建议每个需求保存：

```text
feature/
  prototype-spec.json
  input/               已获准保存的资料或来源引用
  prototype/           原型源码和模拟数据
  acceptance/          报告、截图及设计师反馈
  export/              后续工具生成的静态包
```

规格可先处于 `intake`，Sens版本和组件映射尚未确定时不能进入 `ready`。Schema只验证结构，不能证明业务正确、组件真实存在或原型通过视觉验收。

## 当前 Sens 接入状态

1. 原型通过固定版本 `@sens/prototype-kit` 使用明确的公开入口，不引用预览站源码。
2. `SensPrototypeProvider` 统一初始化主题、字体、国际化和提示运行时。
3. `SensProductShell` 提供标准 T 型 / 上下布局、正式顶导、侧导、标题栏、滚动控制和回到顶部。
4. Logo 与当前导出的图标资源已进入资产包，不依赖预览站根路径。
5. Sens 组件内部仍可使用 antd；业务原型不得直接导入 antd。
6. 长表格“标题栏随流 + 表头唯一吸顶”仍是后置特殊模式，不阻塞第一批 PM 试点。

第一批试点只使用 `catalog.json` 中登记并经过验证的能力，不等待所有基础组件齐全。

## 独立构建与交付验证

另一台已安装 Node.js 与 npm、并且能够访问 npm 软件源的机器，可以复制或克隆整个 `sens-prototype` 仓库后执行：

```bash
cd examples/feature-selection/prototype
npm ci
npm run build
npm run preview
```

静态产物位于 `examples/feature-selection/prototype/dist`。它必须通过 HTTP 服务访问，不能用双击 `index.html` 代替部署验证。

仓库维护者可以在项目根目录执行以下命令完成 P0-5A 的干净副本检查：

```bash
node scripts/verify-portable-delivery.mjs
```

脚本会复制一份不含 `.git`、`node_modules` 和 `dist` 的临时仓库，重新安装、构建，并检查 HTML、JavaScript、CSS、个人绝对路径及内部 npm 地址。临时副本默认在检查结束后删除；需要保留排查时使用 `KEEP_DELIVERY_TMP=1`。
